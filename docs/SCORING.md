# The compatibility algorithm

This document is the single source of truth for **how a listing's match % and
per-feature compatibility are computed, and how each preference feeds in.** It
exists because subtle scoring bugs (a listing in a wanted neighborhood shown as
a location "deficit"; every listing's amenities row cratered to red) are easy to
ship and hard to notice. If you change ranking, read the **Design invariants**
section first — most of our scoring bugs were a violation of one of them.

Everything here lives in three files:

- `knn.py` — the soft score (`distance()`), weights, and match % (`match_pct()`).
- `engine.py` — the hard gate (`acceptable_rules()`) and the two-stage `rank()`.
- `web.py` — how the score becomes the UI's compatibility panel (`_deltas`,
  `_trust`, `_priority_map`) and the sort-only nudges.

Tests: `tests/test_functionality.py` (soft score per feature), `tests/test_engine.py`
(gate + rank).

---

## 1. Two stages: a hard gate, then a soft score

Ranking is deliberately split so feedback can never cause drift:

1. **Hard gate (constraints).** A listing must pass *every* rule derived from
   your preferences or it's discarded — no score can resurrect it.
2. **Soft score (objectives).** Survivors are ordered by a weighted distance to
   what you asked for. Closer = better.

> **Core principle — constraints vs. objectives.** A constraint must hold
> (budget ≤ cap); an objective is optimized (as close to ideal as possible).
> Keeping them separate is what makes budget/location violations *impossible*
> rather than merely unlikely.

The displayed **match %** comes from the soft score:

```
match% = round(100 · e^(−distance / 1.4)),  clamped to [0, 100]
```

Exponential, not linear: near the top small differences matter a lot (distance
0 → 100 %, 0.5 → ~70 %), far away they don't (3.0 vs 3.5 are both "bad").

## 2. The soft score (per-feature distance)

Each listing becomes a point in a six-feature space. Every feature produces a
`part` value in roughly `[0, 1.5]` (0 = perfect, higher = worse), and the total
distance is a **weighted Euclidean** combination:

```
distance = sqrt( Σ_feature  weight[feature] · part[feature]² )
```

### Default weights (`DEFAULT_WEIGHTS`)

| Feature   | Weight | Why |
|-----------|:------:|-----|
| price     | 3.0    | the dominant real-world constraint |
| beds      | 2.5    | usually a hard need |
| location  | 2.0    | second only to price/beds for most renters |
| amenities | 1.5    | matters, but data is sparse (see §5) |
| baths     | 1.0    | usually a floor, not a target |
| sqft      | 0.8    | often unreported; a soft nudge |

Weights can be **learned** from your likes (`learn.py`, ≥5 likes) and override
the defaults — but learning affects only the soft score, never the gate.

### Per-feature formulas

All "preference" queries are **directional**: being *better* than you asked
(cheaper, more baths, more sqft, more beds) is **free**, only shortfalls cost.
"Seed" queries (the *similar* view) are symmetric — see §6.

- **price** — `price_scale = max(0.35 · target_price, 500)`.
  Directional: `0` anywhere within `[min_price, max_price]`; over budget
  `2.5·(price − max)/scale`; under the floor `(min − price)/scale`. Capped at 3.0.
  (`target_price` aims ~8 % below max so "at budget" isn't treated as far.)
- **beds** — `d = (want − have)` if fewer than wanted, else `0.5·(have − want)`;
  `part = min(|d|/2, 1.5)`. **Fewer beds than wanted hurts twice as much as extra.**
- **baths** — fewer than wanted → `(want − have)`; extra → `0` (directional).
  `part = min(|d|/2, 1)`.
- **location** — each wanted neighborhood is an **area, not a point**. The part
  is the distance to the nearest area's **edge**, `/ 8`, capped 1.5 — **`0` when
  the listing is inside a wanted neighborhood**, even off-center. The area is
  (`models.area_edge_km`):
  - a **precise NTA boundary polygon** when available — inside → 0, else distance
    to the boundary. Generated by `scripts/build_neighborhoods.py` from NYC Open
    Data into `neighbors/neighborhoods.json` (optional; free).
  - otherwise a **disk** whose radius = half the distance to the nearest other
    neighborhood centroid, clamped to `[0.7, 2.5]` km (`NEIGHBORHOOD_RADIUS`).

  Always the **nearest** wanted neighborhood, never the centroid of all
  (invariant L). Unknown coordinates → `0.4` (mild, not disqualifying).
- **sqft** — only when you set a `min_sqft` and the listing reports sqft: below
  min → `(min − sqft)/600` (capped 1); extra is free (directional). `min_sqft`
  set but listing sqft **unknown** → `0.3`. No `min_sqft` → `0`.
- **amenities** — see §5 (the three-tier model). If you want none → `0`.

## 3. The hard gate (constraints)

`engine.acceptable_rules(prefs)` builds a declarative list of `(name, predicate)`.
A listing must satisfy all applicable rules. Rules that don't apply (no floor
set, no neighborhoods chosen) simply aren't added.

| Rule | Applies when | Keeps a listing if |
|------|--------------|--------------------|
| `price_cap` | always | `price ≤ max_price · (1 + price_stretch)` (stretch 0.15) |
| `beds_floor` | always | `beds ≥ wanted beds` |
| `borough` | boroughs chosen | in a chosen region, near it (border buffer), or **coords unknown** |
| `price_floor` | `min_price` set | `price ≥ 0.85 · min_price` (small slack) |
| `sqft_floor` | `min_sqft` set | `sqft is None` **or** `sqft ≥ min_sqft` |
| `location` | neighborhoods chosen | within 8 km of **any** wanted neighborhood, or coords unknown |
| `amenities` | must-haves chosen | listing reports **no** amenities, **or** wanted ⊆ reported |
| `not_excluded` | anti-prefs set | not in / within 1.5 km of an excluded neighborhood |
| `commute<place` | a place has a **hard** time limit | transit time ≤ `max_min`, or commute can't be estimated |

Note how many rules end in "…**or unknown**". That's the **unknown ≠ absent**
principle (invariant U): missing data never excludes a listing.

## 4. How each preference factors in (quick reference)

| Preference | Gate rule(s) | Soft-score feature | Directional? |
|------------|--------------|--------------------|:------------:|
| Max rent | `price_cap` (cap × 1.15) | `price` (hard over budget) | yes |
| Min rent | `price_floor` | `price` (mild under floor) | yes |
| Bedrooms | `beds_floor` | `beds` (fewer costs 2×) | yes |
| Bathrooms | — | `baths` (fewer only) | yes |
| Boroughs / cities | `borough` | — (coarse filter only) | — |
| Neighborhoods (want) | `location` (≤8 km of any) | `location` (nearest disk edge; 0 if inside) | — |
| Neighborhoods (avoid) | `not_excluded` | — | — |
| Amenities | `amenities` (unknown-safe) | `amenities` (three-tier) | — |
| Min sqft | `sqft_floor` | `sqft` (below min only) | yes |
| Important place + **hard** time cap | `commute<place` | — | — |
| Important place + **soft** time cap | — | sort-only penalty (§7) | — |
| Prioritize verified | — | sort-only penalty (§7) | — |
| Drawn map area / "search this area" | replaces boroughs+neighborhoods for that query (bbox / polygon) | — | — |

## 5. Amenities — the three-tier model

Rental sources publish little structured amenity data, so a listing arriving
with an empty amenity list is normal. Three tiers, never conflated:

- **Reported** (`amenities`) — what the source stated; the *complete* set the
  **gate** reasons about.
- **Derived** (`derived_amenities`) — high-confidence **facts** from
  authoritative records (elevator from PLUTO class; central_air/parking from a
  RentCast property lookup). Credit the soft score, kept **separate** so they
  can't flip the gate into strict mode.
- **Inferred** (`inferred_amenities`) — **guesses** from building size/age.
  Advisory display only: never gate, never score.

Soft-score formula (`part["amenities"]`), when you want ≥1 amenity:

- Source reported amenities → `1 − matched/wanted`, where `matched` counts
  wanted amenities present in `reported ∪ derived`.
- Source reported **nothing** → `0.4 · (1 − confirmed/wanted)`, where
  `confirmed` = wanted amenities we can confirm from `derived`. This is the
  **unknown ≠ absent** rule: no data is a *mild* penalty, not a total miss.

## 6. Beyond the score: seeds, blend, and truncation

`rank()` = gate, then:

```
score = α · distance_to_preferences  +  (1 − α) · min(distance_to_each_liked_listing)
```

- **Liked listings** become extra magnets (`Query.from_listing`, symmetric mode).
  `α` (default 0.6, the "Rank by" control) is the drift knob: 1.0 ignores likes.
- Liked/hidden listings are excluded from results; likes act only as seeds and
  **can never pull results outside the gate**.
- The list is truncated to `k` (Results to show) **after** the sort-only nudges.

---

## 7. Sort-only nudges (must NOT change match %)

`web._priority_map` produces a per-listing penalty **added to the sort key
only** — `Ranked.score` (and therefore match %) is left untouched:

- **Verification priority** — `strength × VERIFY_PRIORITY[level]`
  (`confirmed 0.0`, `unverified 0.15`, `caution 0.6`); strength off/gentle/strong
  = `0 / 1 / 2`.
- **Soft commute limits** — each soft place over its `max_min` adds
  `min(over/20, 1.0)`.

This is why a verified 71 % can rank above an unverified 74 % without either
match % changing. See invariant P.

## 8. What the UI shows (the compatibility panel)

The panel is a direct read-out of the `parts` above (no separate math):

- **Per-feature fit** = `max(0, round(100 · (1 − part[feature])))`. 100 = exactly
  what you asked for. (Note this is a *per-feature linear* mapping, distinct from
  the overall exponential `match_pct` — don't conflate them.)
- **Row order** = `part[feature] · weight[feature]` descending — i.e. what's
  actually costing the listing the most points.
- **Plain-language notes** come from `_deltas`: "$180 over budget", "1.4 km from
  your area" (nearest neighborhood), "1 bed fewer than you want", "size not
  listed", "missing dishwasher", "amenities not listed".
- Perfect rows are compressed to one green line; weight shown as `•/••/•••`.

## 9. Design invariants (read before changing ranking)

These are the rules whose violation has caused — or would cause — bugs. Every
one has a regression test; keep it that way.

- **U — Unknown ≠ absent.** Missing data is a *mild* penalty in the score and a
  *pass* in the gate, never worst-case. Holds for amenities (0.4 unknown), sqft
  (0.3), location (0.4 for missing coords), and every "…or unknown" gate rule.
  *Violated once →* every data-less listing scored amenities as a total miss and
  match % cratered across the board.
- **L — Location is a nearest-neighborhood AREA, not a point/centroid.** Two
  parts: (1) distance is to the **nearest** wanted neighborhood, never the
  centroid of all of them; (2) each neighborhood is a **disk**, so a listing
  *inside* it scores `0` even off-center — distance is measured from the disk
  edge, not the center. Holds in the soft score, and the "N km from your area"
  delta (`area_edge_km`). *Violated once each →* wanting two spread-out
  neighborhoods put the target between them (the Financial District bug); and
  representing a neighborhood as its centroid penalized in-neighborhood listings
  for being off-center. Now resolved with per-neighborhood areas (precise NTA
  polygons when built, disks otherwise).
- **P — Sort-only nudges never change match %.** Verification priority and soft
  commute penalties are added to the sort key only; `Ranked.score` stays pure.
  Otherwise trust/commute would masquerade as preference fit.
- **D — Directionality.** In preference mode, *better than asked* is free
  (cheaper, extra beds/baths/sqft). Only shortfalls cost. Don't penalize a $3,200
  listing when your cap is $3,500.
- **G — Likes never escape the gate.** `α` only reorders inside the acceptable
  region; a liked expensive place can't pull over-budget listings in.
- **F — Facts vs guesses.** Derived amenities (facts) credit the score and are
  gate-safe by living in a *separate* field; inferred amenities (guesses) touch
  neither gate nor score. Never merge either into `amenities` (that would flip
  the amenity gate into strict mode and wrongly exclude listings).
- **S — Keep parts in ~[0, 1.5].** Every feature's `part` must be scaled and
  capped so no single feature dominates the weighted sum. If you add a feature:
  add it to `DEFAULT_WEIGHTS`, give it an unknown-data branch (invariant U), and
  cap it.

## 10. Worked example

Preferences: max_price $4,000, 1 bd, neighborhoods = {Financial District,
Astoria}. Listing: **90 Gold St, Financial District, $3,800, 1 bd, 1 ba**, no
amenity data, coordinates known.

| Feature | part | Why |
|---------|:----:|-----|
| price | 0.0 | $3,800 ≤ $4,000 → within budget, free (directional) |
| beds | 0.0 | 1 bd = wanted |
| baths | 0.0 | 1 ba, no bath preference shortfall |
| location | **0.0** | it *is* inside the Financial District disk → 0 (invariant L) |
| sqft | 0.0 | no `min_sqft` set |
| amenities | 0.0 | none wanted |

`distance = sqrt(0) = 0` → **match 100 %**. Under the old centroid bug, location
would have been ~0.61 (4.9 km to the FiDi+Astoria midpoint), dragging the match
down for an apartment sitting exactly where you asked.

## 11. Changing the algorithm safely

- The whole soft score is **one function**: `distance()` in `knn.py`. Gate rules
  are **one function**: `acceptable_rules()` in `engine.py`.
- To add a feature: extend `Query`, add its `part` (scaled, capped, with an
  unknown branch), add a `DEFAULT_WEIGHTS` entry, and — if it's also a
  constraint — a gate rule. Add tests in `test_functionality.py` (score) and
  `test_engine.py` (gate).
- Anything that should reorder but not change match % goes in
  `web._priority_map` as a sort-only penalty, not into `distance()`.
